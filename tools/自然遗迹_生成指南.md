# 自然遗迹：从存档建筑到世界生成

本文对应 `world/AddonStructures.java`（已建好骨架）与 `config/MNGA/worldgen.cfg` 里的
`structure*` 配置项。按顺序做完这几步，遗迹就会跟着 HBM 的结构系统一起生成。

---

## 0. 一句话方案

**不自己写 `IWorldGenerator`，而是往 HBM 的 `NBTStructure` 静态注册表里塞一条 `SpawnCondition`。**

HBM 的 `NTMWorldGenerator` 已经处理好了一切：

| 它负责的事 | 具体行为 |
|---|---|
| 决定在哪生成 | 把世界切成 4~12 区块的网格（`StructureConfig.structureMinChunks/MaxChunks`），每个格子最多一个结构槽位 |
| 决定长哪个结构 | 按生物群系过滤 + 权重随机 |
| 决定多高 | 取该地形平均高度，clamp 到 `minHeight~maxHeight` |
| 写方块 | 监听 `PopulateChunkEvent.Pre`，逐区块裁剪后写入，跨区块不会重复写 |
| 旋转 | `BlockDummyable` / 楼梯 / 朝向方块都有 `INBTBlockTransformable`，自动转 |

自己再注册一个 `IWorldGenerator` 反而会出问题：`NBTStructure` 的 `spawnMap` 是 **static** 的，
两个生成器都能查到同一张表，同一位置会被生成两次。

## 1. 在存档里导出建筑

### 1.1 拿到工具方块

| 方块 | 注册名 | 用途 |
|---|---|---|
| 结构保存方块 | `hbm:tile.wand_structure`（meta **0**） | 把选区存成 `.nbt` |
| 结构加载方块 | `hbm:tile.wand_structure`（meta **1**） | 把 `.nbt` 贴回世界（摆完检查用） |
| 结构魔杖方块（空气） | `hbm:tile.wand_air` | **在结构内部标记「这里必须是空气」** |
| 结构魔杖方块（战利品） | `hbm:tile.wand_loot` | 概率战利品占位箱（见第 5 节 B 方案） |

它们不在创造模式物品栏里，用 `/give` 拿：

```
/give @p hbm:tile.wand_structure 1 0
/give @p hbm:tile.wand_air 64
```

> **注册名带 `tile.` 前缀**，写成 `hbm:wand_structure` 会报「物品不存在」。
> 原因：HBM 的 `ModBlocks.register(Block)` 是
> `GameRegistry.registerBlock(b, ItemBlockBase.class, b.getUnlocalizedName())`，
> 而 `getUnlocalizedName()` 对方块返回 `"tile." + 名字`。所以游戏内一律是
> `hbm:tile.xxx`（其它 HBM 方块同理，见参考手册第 11900 行后那张表）。
> 如果懒得打字，也可以用 `/give <玩家> <数字ID>`，ID 在游戏日志里
> `[structure] 结构工具方块 ID（创世神填充用）` 那一行已经打印出来了。

### 1.2 放保存方块的位置（最容易错的一步）

`saveStructure()` 的实际保存范围是：

```
(x, y+1, z) ~ (x+sizeX-1, y+sizeY, z+sizeZ-1)
```

也就是说**方块自己占的那一格不算在内，保存从它正上方开始**。所以：

```
把结构保存方块放在  建筑在 X/Z 轴正方向的最小角、最底层再往下一格
```

举例：建筑占据 `(100..129, 64..83, 200..229)`（30×20×30）
→ 方块放在 `(100, 63, 200)`，GUI 里填 `sizeX=30, sizeY=20, sizeZ=30`。

### 1.3 保存：GUI 里就四个输入框

右键保存方块（不要潜行；潜行是加黑名单，见 1.3.1）打开面板：

```
[ 名字                    ]   ← 文件名，不要带路径和后缀
[ sizeX ] [ sizeY ] [ sizeZ ] ← 保存范围的三边长度（格数），不是坐标

            [   SAVE   ]
```

点 SAVE → 面板关闭 → 聊天栏出现 `Saved structure as xxx.nbt`，
**点这行文件名可以直接打开文件夹**。

文件落在 **`.minecraft/structures/<名字>.nbt`**（开发环境是 `run/structures/`）。
名字只能是简单文件名：`structuresFile()` 会做 `getCanonicalFile()` 校验，
带 `../` 或子目录的名字会被判为 `invalid name`。

`sizeX/Y/Z` 和坐标的关系再确认一遍（`saveStructure()` 原文）：

```java
quickSaveArea(name + ".nbt", world, x, y + 1, z, x + sizeX - 1, y + sizeY, z + sizeZ - 1, blacklist);
```

| 方向 | 范围 |
|---|---|
| X | `x ~ x+sizeX-1`（**含**方块自己所在的那一列） |
| Y | `y+1 ~ y+sizeY`（**不含**方块自己那格，从正上方开始） |
| Z | `z ~ z+sizeZ-1`（**含**方块自己所在的那一列） |

所以尺寸 = 建筑的外接盒边长，方块本身永远不会被存进文件里。

体积上限 `MAX_SAVE_VOLUME = 8×1024×1024` 格（约 200 万），实际用不到。

#### 1.3.1 保存前先确认「盒子里装的是什么」

导出会把盒子里**所有非空气方块**都存下来，包括你不想要的地形（沙子、泥土、草）。
两种处理方式：

- **地形无害**：留着。生成时这些方块会把地形盖掉，正好当基座。
- **地形多余**：潜行 + 手持要排除的方块右键保存方块 → 该方块进入黑名单
  （准星对着保存方块时会显示黑名单列表），导出时跳过。同一操作再点一次是移出。

`hbm:wand_*` 系列方块和空气**不能**加进黑名单（`ModBlocks.isStructureBlock` 挡着）。

#### 1.3.2 保存完想验证

拿 meta 1 的加载方块放在同一位置 → GUI 里选文件 → LOAD，会把结构原样贴回来。

**注意加载方块没被红石供能时会进调试模式**（`ServerConfig.STRUCTURE_DEBUG`），
空气标记会变成可见方块——这是故意的，方便你看出「哪里被标成了空气」。

### 1.4 ⚠️ 内部空腔：必须显式标记，否则埋进土里

这是整个流程唯一的硬坑。

**规则只有三条：**

| 导出时盒子里那一格是… | 生成时会… |
|---|---|
| 普通方块（石头、箱子、机器…） | **强制覆盖**成那个方块 |
| `hbm:tile.wand_air` | **强制挖空**成空气（`BlockWand.exportAs = Blocks.air`） |
| 空气 | **跳过，保留原地形**（`saveArea` 把空气加进黑名单，`build()` 里 `state == null` 就 `continue`） |

所以「空气」是**不存在**的：没记录的格子什么都保留。地下遗迹被土埋死、
房间和机器全是石头、箱子打不开，都是因为房间内部没有用 `wand_air` 标记过。

#### 1.4.1 本体遗迹是怎么做的（实测数据）

我把 HBM 自带的 45 个 `.nbt` 全解析了一遍：**只有 3 个带空气条目**，
而且空气只出现在室内：

| 结构 | 盒子体积 | 实体 | 空气条目 |
|---|---|---|---|
| `desert_shack_1` | 18×13×16 = 3744 | 1279 | **345**（只标了 y=8~11 的室内，屋顶以上一条都没有） |
| `factory` | 38×41×19 = 29602 | 5840 | **2775** |
| `laboratory` | 19×17×21 = 6783 | 1612 | **365** |
| `lighthouse` | 65×72×66 = 308880 | 52053 | **0**（架空的高塔，本来就长在空气里） |

结论：**只标「玩家能站能看见」的封闭空间**，不要整个盒子都铺。
`desert_shack_1` 盒子里的空格有 2120 格，作者只标了 345 格——剩下 1775 格是屋顶上方的天空，
标了就等于在半空挖一个大方洞。

#### 1.4.2 方案 A：创世神一键填充（推荐）

`wand_air` 在 1.7.10 的创世神里**不能用名字**，只能填数字 ID。
启动时日志里会打出来（`AddonStructures#register` 第一行）：

```
[structure] 结构工具方块 ID（创世神填充用，仅本次加载有效）:
wand_air=1234 → 填内部空气用 `//replace air 1234`；wand_structure=1235 → 手放保存方块用 `//set 1235`
```

**这个数字没有固定值**——1.7.10 的方块 ID 由 FML 按注册顺序分配，多装/少装一个模组、
或者改变加载顺序，数字就会变。所以：

- 每次开游戏后重新看日志（搜 `结构工具方块 ID` 或 `wand_air=`，在
  `.minecraft/logs/latest.log` / `fml-client-latest.log` 里）；
- 别把别人教程里的数字抄过来，会填到别的方块上；
- NEI 悬停物品时 tooltip 右上角也会显示当前 ID，可以对照。

##### 本机实测值（HBM 5852 测试客户端，2026-11-11）

日志没打出来（jar 还没重打包）时，可以直接从存档反查：区块里 `TileEntities`
存的是 TE 注册名，`Sections.Blocks` 存的是数字 ID，用 TE 坐标对回去就得到 ID
（工具：`python tools/blockid_probe.py "<存档目录>"`）。

推导链：世界里 `tileentity_ntm_logic_block` 共 24 个，方块 ID 只落在 **1958(2 个)**
和 **1959(22 个)** 上；`LogicBlockInvis extends LogicBlock` 共用同一个 TE，而
`BlockWandLogic` 第 247 行默认把 wand_logic 转成 `logic_block_invis`（隐形的多，
22 个），所以 `logic_block_invis = 1959`、`logic_block = 1958`。再按
`ModBlocks.registerBlock()` 里的注册顺序往前退 7 格：

| 方块 | 注册名 | ID |
|---|---|---|
| 空气标记 | `wand_air` | **1952** |
| 战利品占位 | `wand_loot` | 1953 |
| 拼图 | `wand_jigsaw` | 1954 |
| 逻辑（魔杖） | `wand_logic` | 1955 |
| 串联 | `wand_tandem` | 1956 |
| 结构保存/加载 | `wand_structure` | 1957 |
| 逻辑方块 | `logic_block` | 1958 |
| 隐形逻辑方块 | `logic_block_invis` | 1959 |

换整合包/加模组后这张表全部作废，必须重新反查或看日志。

填之前先验一下：`//set 1952` 单点一个方块，看贴图是不是 `wand_air` 那个小方块；
如果是带纹路的逻辑方块，说明整体偏了一格，换成 1953 再试（`//undo` 可撤）。

如果你的创世神版本支持注册名，先试 `//replace air hbm:wand_air`，能用就不用管 ID。

拿到 ID 之后：

```
1. 木斧选「内部空腔」两个对角（只选房间/走廊/机房，不要选到屋顶以上的天空）
2. //replace air 1234        ← 只把选区里的空气换成 wand_air，建筑本体一格不动
3. //undo                     ← 填错了随时撤（导出前记得把 wand_air 留着）
4. 右键保存方块 → 填尺寸 → SAVE
```

几个要点：

- **`//replace` 不会碰建筑**，因为它只替换「本来空气」的格子。千万别用 `//set`，
  那会把整个选区刷成同一种方块。
- **选区必须是「腔内」而不是「盒子」**：屋顶上方、建筑外侧的空气不要选进去。
- `wand_air` 看起来是**悬空的小玻璃方块、无碰撞**，可以直接穿过去，肉眼就能核对填得对不对。
- 导出后想清理现场：`//replace 1234 air`（注意顺序反过来了）。
  不清理也没关系，它不会参与生成，也不影响后续存档。

#### 1.4.3 方案 B：不用创世神，后处理 .nbt

没有创世神（或者懒得一个房间一个房间选）时，用仓库里的脚本整盒填充：

```bash
# 先体检：尺寸、方块数、有没有空气条目
python tools/structure_air_tool.py <导出的.nbt> --info

# 预览会填多少格
python tools/structure_air_tool.py <导出的.nbt> --dry-run

# 真填（自动备份成 .nbt.bak）
python tools/structure_air_tool.py <导出的.nbt> -o <assets下的目标路径>
```

它的规则很简单：**把外接盒里所有「没记录」的格子补成 `minecraft:air`**。

- 对**规整的方形地下建筑**，外接盒 ≈ 建筑外壳，等价于「挖空内部」，可以直接用。
- 对**L 形 / 不规则建筑**，盒子四角会在地形上多挖出缺口；这时候用方案 A。
- 它会先跑一遍 `--info` 的体检输出，**已经有空气条目就不要再跑**（会重复加条目）。
  `--dry-run` 显示的「待填空气 0 格」就是这个意思。

脚本只依赖 Python 标准库，45 个本体结构全部做过读写往返比对（解析→写出→再解析，
逐字段一致），不会破坏文件结构。

#### 1.4.4 方案 C：什么都不做

以下两种情况可以完全跳过这一节：

- 建筑整栋在地面以上（地基以下是实心），房间本来就在空气里；
- 你**就是要**让它被埋住（地堡、陨石砸出来的半埋遗迹），那正好利用「保留原地形」。

## 2. 放进资源目录

```
src/main/resources/assets/makentmgreatagain/structures/mnga_structure_geocentric_laboratory.nbt
```

路径必须和 `AddonStructures.RUIN_NBT` 一致。当前用的是「地心实验室」：

| 项 | 值 |
|---|---|
| 结构文件 | `structures/mnga_structure_geocentric_laboratory.nbt` |
| 注册名 / piece 名 | `mnga_geocentric_laboratory` |
| 尺寸 | 41 × 13 × 38（20254 格） |
| 生成维度 | -1（下界） |
| 底座高度 | 0 ~ 3（clamp 到固定层位，实际落在 y=3） |

`NBTStructure` 是用 `getResourceAsStream("/assets/<modid>/<path>")` 读的，
所以开发环境（`build/resources/main`）和打包后的 jar 都能读到。

⚠️ 直接从游戏里导出的 `.nbt` 不能直接放进来——它里面一条空气都没有（空气被
`saveArea` 的黑名单跳过了），生成时整个盒子会保留原地形，房间会被土填死。
必须先过一遍 1.4.3 的补空气流程，或者用下面这条一次搞定：

```
python tools/structure_air_tool.py "<导出目录>/mnga_structure_geocentric_laboratory.nbt" \
    -o src/main/resources/assets/makentmgreatagain/structures/mnga_structure_geocentric_laboratory.nbt
```

## 3. 注册参数

代码已经写好，位置 `com.makentmgreatagain.world.AddonStructures#register()`，
在 `MakeNTMGreatAgain#postInit` 末尾调用。

**结构文件不存在时会只打一条 warn 并跳过**，不会崩：

```
[MNGA-Structures] [structure] 找不到 assets/makentmgreatagain/structures/mnga_structure_geocentric_laboratory.nbt，跳过遗迹注册
```

可调参数全在 `config/MNGA/worldgen.cfg` 的 `worldgen` 段：

| 配置键 | 默认 | 说明 |
|---|---|---|
| `enableStructureWorldgen` | true | 总开关 |
| `structureGridChunks` | **11** | 自定义间距（区块），平均每 11² = **121 区块一处** |
| `structureSpawnWeight` | 6 | 权重。走自定义坐标通道时**不参与抽签**，留着只为和其它结构对照 |
| `structureDimensionId` | **-1** | 0 主世界 / -1 下界 / 1 末地 |
| `structureMinHeight` | **0** | 结构**底座**高度下限（不是中心） |
| `structureMaxHeight` | **3** | 上限；与下限相等即固定在那一层 |
| `structureHeightOffset` | **0** | 结构整体上下平移，-1 让地板与地面齐平；被 clamp 到固定层位时无影响 |
| `structureLootRandomize` | **true** | 箱子内容随机化：按稀有度/数量决定每格留不留，再打散到随机格子 |

⚠️ 下界的 0~4 层是基岩。底座落在 y=3 时，结构自己的地板层（整层实心）正好压住基岩，
不会再往上挖洞；但如果把 `structureMinHeight` 改成 0，空气条目会替掉 y=0 的基岩，
玩家在那层能直接看到虚空——别让玩家在那层挖。想稳妥就把 0/3 改成 4/4。

### 层位是怎么定的（⚠️ 超平坦存档的坑）

HBM 自己那套层位逻辑是：

```java
int y = isFlatWorld ? averageHeight                                   // 超平坦：直接用地表高度
                    : MathHelper.clamp_int(averageHeight, min, max);  // 正常世界：夹进 min~max
```

**问题是「超平坦」那一支完全跳过 clamp。** 而「地表高度」取的是
`world.getTopSolidOrLiquidBlock()`，在地狱里返回的是**天花板**（y≈127）。
于是同一份配置：

- 正常存档：`clamp(127, 0, 3) = 3` → 结构在 y=3~15，埋在地狱岩里（设计如此）；
- **超平坦存档：`y = 127`** → 结构整座搬到 y=123~135，卡在基岩顶上面。

`AddonStructures.RuinStart#pinHeight()` 就是为了堵这个洞：进 `super.generateStructure()`
之前自己算一遍 `clamp(平均地表高度, min, max)`，再把组件整体挪过去。
挪动走的是 `Start.offsetYHeight()`，它顺手把组件标成 `heightUpdated = true`，
HBM 后面那条分支就不会再动它。`delta == 0` 时也必须调一次，否则标记不上、照样被挪走。

所以：**别指望 HBM 的 `minHeight/maxHeight` 在超平坦存档里生效**，被测结构一定要在
`RuinStart#generateStructure` 里先把层位钉死。

钉住之后会打一条日志，直接告诉你落在了哪：

```
[MNGA-Structures] [structure] 地心实验室已生成: 底座 y=3，平面范围 x=-56~-16, z=-120~-83（区块 -4,-8 附近）
```

### 怎么确认「到底生成了没有」

在游戏里飞着找是最低效的办法：121 区块一处、还埋在实心地狱岩里，
走 50 个区块没撞见完全正常。用 `tools/structure_find.py` 直接读存档：

```bash
# 这座实验室里有 10 个钢箱（tileentity_crate_steel），拿它当指纹把已生成的都揪出来
python tools/structure_find.py "F:/.../eclipse/saves/新的世界"

# 顺带按世界种子反推「网格公式说哪里该有」，去没探索过的区块蹲点
python tools/structure_find.py "<存档目录>" --predict 10

# 改过 structureGridChunks 就把同一对数告诉它，否则预测对不上
python tools/structure_find.py "<存档目录>" --predict 10 --grid 7
```

输出会给每座实验室的簇、钢箱数量、`y`、平面中心，以及一条 `/tp` 命令：

```
  [ 7] 区块 (5, 7) ~ (6, 8)   钢箱 10 个   y=129/135
       底座大约 y=123，平面中心 (94, 122) → /tp @p 94 123 122
```

工具只读存档，不改任何东西。`y=129/135` 这种高层就是上面那个超平坦 bug 的特征值。

### 生成密度怎么控制（`structureGridChunks`）

HBM 的结构是「槽位制」：全局每 `StructureConfig.structureMaxChunks`（默认 12）区块开一个槽位，
槽位里按权重抽一个结构，抽到 null 就什么都不长。**这套网格是全局的**——
在 HBM 里调它会把主世界的废墟、实验室、油井一起改密，不能只改我们的。

所以这个结构不走槽位，改走 `SpawnCondition.checkCoordinates` 这条「每个区块都问一次」的
独立通道，自己排格子：

```java
int gx = Math.floorDiv(chunkX, spacing);         // 11×11 区块的格子
long h = 世界种子 ^ gx*hash1 ^ gz*hash2 ^ 维度;   // 稳定 hash
int span = spacing - 4, base = 2;                // 两头各留 2 区块
int ox = base + h % span, oz = base + (h>>>32) % span;
return chunkX == gx*spacing + ox && chunkZ == gz*spacing + oz;
```

- **密度 = spacing² 区块一处**：11 → 121 区块（≈193×193 格），12 → 144，16 → 256。
- 落点由 hash 决定，**同一存档每次询问答案一致**（不会读档后又长到别处），
  也不会像纯随机那样两座实验室贴在一起。
- 落点两头留 2 区块，所以相邻两点的最小间距是 5 区块（80 格）＞ 结构宽度 41 格，
  不会出现两座实验室互相切进去。间距设到 6 以下时留边量会自动收窄，但底限仍是 5 区块。
- 想再稀一点就调大；4 以下会让 41×38 的实验室互相压住，不建议。

### 权重怎么理解（走 HBM 槽位时才用得上）

槽位里按权重抽一个结构（或抽到 null 什么都不长）。参照本体的取值：

| 结构 | 权重 |
|---|---|
| ruinA ~ ruinJ（废墟） | 10 |
| desert_shack | 5~7 |
| crashed_plane | 5~8 |
| tower_base / radio_house | 6 |
| factory / laboratory | 10 |

想要「比废墟稀一点」设 2~4，「常见」设 10 以上。

### 生物群系过滤

骨架里默认是：

```java
非水域 && 非海洋 && heightVariation <= 0.35F
```

也就是平原/森林/丘陵，不会出现在海里，也不会长在悬崖上。
按需要改 `isValidBiome()`，比如只允许沙漠：

```java
return BiomeDictionary.isBiomeOfType(biome, Type.SANDY);
```

放到下界时这条过滤不用改：下界生物群系（Hell）不在 WATER/OCEAN 里，
`heightVariation` 是 0.2（默认值），天然满足条件。

## 4. 箱子：把导出时的内容当模板，按稀有度随机

导出结构时箱子里摆的东西照样存进 NBT，但生成时**不再原样照搬**，而是当模板重新掷一遍：

1. 逐格判定：按物品的稀有度 + 这一格原来的数量，决定「留不留」；
2. 留下的重新掷数量：原数量的**四成 ~ 原数量**；
3. 整箱清空，再把留下的物品塞进**随机空格**——不会再按 0、1、2… 排成一列。

开关是 `structureLootRandomize`（默认开）。关掉就完全按 NBT 原样生成。
实现见 `world/AddonStructures.java` 的 `randomizeContainer()`。

### 4.1 稀有度与保留概率

| 档位 | 基础保留率 | 归入这一档的物品 |
|---|---|---|
| `COMMON` | **90%** | 建材、钢/铅/钛锭、管道、储罐、钢桶、脚手架、红电缆、煤粉/铁粉/灰粉/铀粉/钠粉、注射器、食物、核废料 |
| `UNCOMMON` | **78%** | 杜拉钢锭、铌粉/钛粉、防护服/石棉服、滤毒罐、radaway、血袋、siox、弹药、污染检测仪、普通金苹果 |
| `RARE` | **62%** | U235 坯、各种燃料棒、PWR 燃料、离心机、机器升级、三把枪、desh 镐、钴剑、电池包 |
| `EPIC` | **45%** | T51 头盔、蒸汽服胸甲/靴 |
| `LEGENDARY` | **30%** | 附魔金苹果（按 meta 单独判） |

数量加成：这一格原来每多 1 个，保留率 **+1 个百分点**，最多 **+15**。
所以「钠粉 ×64」必留，「钢锭 ×2」90%，「电池包 ×1」还是 62%。

单格独立判定——同一箱里的物品各掷各的，才会出现「管道留了一半、机器全没了」这种组合。
按当前参数模拟 2 万次：11 个箱子原有 99 格，生成后平均保留 **79.5 格（80%）**，
每箱平均 7.2 格；最惨的是装备箱（原 6 格）平均剩 3.4 格，最稳的是钠粉箱（原 4 格）几乎不变。

### 4.2 位置与特殊物品

- **位置**：整箱清空后从随机空格里挑，待放列表先 `Collections.shuffle` 打乱，
  所以同样 8 件东西每次落点都不同，看上去是散的。
- **成书**（`written_book`）带正文 NBT，属于剧情物品：原样保留、不掷骰、数量不变。
- **枪 / 护甲 / 电池**：用 `ItemStack.copy()` 迁移，`tag` 里的弹药、充能、燃料全部保留。
- 箱子满了就丢弃剩下的（结构不会为此回滚）。

想整体调稀/调密只改 `Rarity` 枚举里那五个基础值，不用动物品分类表。

### 4.3 什么方块算「箱子」

```java
private static final Block[] LOOT_CONTAINERS = {
        Blocks.chest, Blocks.trapped_chest,
        ModBlocks.crate_iron, ModBlocks.crate_desh
};
```

注意是 **HBM 的 `com.hbm.blocks.ModBlocks`**，不是附属的同名类。

- `crate_iron` / `crate_desh` 是 `BlockStorageCrate`，有 `TileEntityCrateIron`，是真正的容器。
- ⚠️ **`ModBlocks.crate`（补给木箱）不是容器**：它 `extends BlockFalling`，右键直接吐物品，
  没有 `IInventory`。放进数组也只会被 `te instanceof IInventory` 挡掉。
- 要加别的容器（保险箱、附属自己的箱子）直接往数组里加，前提是它有实现 `IInventory` 的 TE。

### 4.4 用 HBM 的 `wand_loot`（B 方案，可选）

如果不想写代码表，也可以用本体自带的占位箱：

1. 在建筑里用 `hbm:tile.wand_loot` 代替箱子；
2. 手持目标容器方块右键它 → 设定「替换成什么」；
3. 螺丝刀调**最少件数**，手钻调**最多件数**；
4. defuser 切换战利品池（`ItemPool.pools` 里的名字）；
5. 导出结构。TE 会把这些设置存进 NBT。

生成时占位方块会在第一 tick 替换成真容器并填 `WeightedRandomChestContent`。

**局限**：池子是按权重抽取 N 次，做不到「这一件必出、那一件按概率」。
要求精确控制就用 4.1 节的稀有度表 + 4.2 节的随机打散。

## 5. 机器里的物品与流体

### 5.1 默认行为：原样保存

`saveArea()` 对每个有 TE 的方块都调用 `te.writeToNBT(nbt)`，
只删掉 `x/y/z` 三个坐标键（生成时会由 `world.setTileEntity` 重新赋值）。

所以：

- 箱子里的物品 ✔ 保存
- 机器输入/输出槽的物品 ✔ 保存（HBM 的 `TileEntityMachineBase` 用 `items` 列表）
- 机器的流体罐 ✔ 保存（`FluidTank.writeToNBT` 写 `<name>_type` 为**流体数字 ID**）

结果：**每个遗迹里那台机器的内容完全一样**。

### 5.2 想让它每次随机

在 `AddonStructures#applyMachineContent` 里按 TE 类型写分支。它在结构生成完、
每个非空气格子的 TE 上各调一次：

```java
static void applyMachineContent(World world, Random rand, int x, int y, int z, TileEntity te) {

    if(te instanceof TileEntityMachineXxx) {
        TileEntityMachineXxx machine = (TileEntityMachineXxx) te;

        // 注意顺序：setTankType 会清空存量，必须先设类型再设量
        machine.tanks[0].setTankType(Fluids.WATER);
        machine.tanks[0].setFill(4000 + rand.nextInt(8000));

        machine.getInventory().setStackInSlot(0, new ItemStack(ModItems.ingot_steel, 4));
        te.markDirty();
    }
}
```

几个要点：

- **`setTankType` 会清空罐**：类型和结构里预置的一样时就不要调用，否则液体归零。
  安全写法：`if(tank.getTankType() != target) tank.setTankType(target);` 然后再 `setFill`。
- **物品槽索引**：HBM 机器普遍是 `TileEntityMachineBase` 的 `slots[]`，
  用 `getInventory()` 或直接 `slots[i]`。具体哪一格是输入，看那台机器的 `Container`。
- **别在 `applyMachineContent` 里做重活**：它在 populate 阶段跑，卡住会拖慢区块生成。

### 5.3 ⚠️ 流体 ID 的稳定性

`FluidTank` 在 NBT 里存的是 `type.getID()`（int）。HBM 的流体 ID 是源码里硬编码的常量，
附属新增流体走 `FluidTypeRegistry.getNewID()` 追加在后面，**不会挤掉 HBM 的 ID**，
所以跨存档是稳定的。

真正的风险是：**同一份结构文件跨 HBM 版本使用**。如果 HBM 大版本调整了流体 ID 表，
机器里的液体会变成别的流体或者 `NONE`。遇到这种情况重新导出一份即可。

## 6. 结构劣化：按概率替换方块

完好无损的建筑每座都一样，多遇到两次就露馅。`AddonStructures.DECAY_TABLE` 在结构落地后
逐格判定，把完好的方块随机换成破败版本。当前「地心实验室」的规则：

| 来源方块 | 替换结果 |
|---|---|
| 强化萤石 `reinforced_light` | 30% → 空气 |
| 耐火砖块 `brick_fire` | 5% → 耐火砖台阶（`brick_slab` meta 6）、10% → 空气 |
| 高密度贫铀混凝土砖块 `brick_ducrete` | 20% → 高密度贫铀混凝土 `ducrete_smooth`、10% → 铀沙（`sand_mix` meta 2） |
| 加固高密度贫铀混凝土 `reinforced_ducrete` | 10% → `ducrete_smooth`、5% → 地狱岩 |
| 黑曜石砖块 `brick_obsidian` | 20% → 黑曜石、4% → 碎黑曜石 `gravel_obsidian` |
| 混凝土砖块 `brick_concrete` | 30% → 开裂 `brick_concrete_cracked`、30% → 破碎 `brick_concrete_broken`、10% → 空气 |
| 铁丝网围栏 `fence_metal` | 10% → 空气 |

> 铀沙在 5852 里没有独立的方块字段：它是 `ModBlocks.sand_mix` 的 `EnumSandType.URANIUM`
> 变体（meta 2），lang 键叫 `tile.sand_uranium`，所以搜 `sand_uranium` 找不到方块定义，这是正常的。

### 判定顺序（重要）

同一方块挂多条结果时是**依次判定、命中即停**，不是各自独立掷骰：

```
耐火砖块 → 先掷 5%：中 → 变台阶
         → 不中，再掷 10%：中 → 变空气
         → 都不中 → 保持耐火砖块
```

所以「5% 台阶 + 10% 空气」的真实占比是 5% + 9.5% = 14.5% 会被动过，剩下的 85.5% 不变。
想让两条规则互不影响（同一格可能叠两次），把 `applyDecay` 里的 `return true` 改成继续循环
——但那样概率就不是你写的那几个数了，一般不这么做。

### 只砸自己放下的方块

`RuinStart.generateStructure` 把处理范围收成「当前区块 ∩ 结构包围盒」：

```java
if(bb.minX > minX) minX = bb.minX;   // X/Z 四个方向都收
...
afterGenerate(world, rand, minX, maxX, minZ, maxZ, minY, maxY);
```

不收紧的话，16×16 区块里落在结构外的那半边自然地形也会被规则扫到，
把世界上原本就有的黑曜石砖、混凝土砖一起砸了——那就不是「废墟」而是「地图破坏」了。

### 对这套结构的影响（期望值）

| | 数量 |
|---|---|
| 参与判定的方块 | 3712 格（黑曜石砖 1291、耐火砖块 899、加固贫铀混凝土 869、混凝土砖 404…） |
| 期望变成空气 | 约 122 格 |
| 期望换形态 | 约 590 格 |
| 最终保留原样 | 约 85% |

## 7. 已知的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| **空腔没标 `wand_air`** | 地下遗迹被土填满，房间是实心的 | 见 1.4，只把「腔内」铺成 `wand_air` |
| **空气铺满了整个盒子** | 遗迹周围（甚至半空）出现一个方形大空洞 | 见 1.4.1：只标封闭的室内，屋顶以上的天空不要选 |
| **保存方块放错位置** | 结构整体偏移一格 | 放在「最小角、最底层下面一格」，见 1.2 |
| **旧世界不生成** | 老存档走了半天没看见 | 结构只在**新区块**生成，必须开新世界或跑远 |
| **超平坦存档层位错乱** | 结构不在配置的 y，而是跑到了 y≈123（地狱）／基岩上方 | HBM 的 `isFlatWorld` 分支跳过 min/maxHeight clamp，直接用「地表高度」；地狱的地表高度是天花板。已在 `RuinStart#pinHeight` 里自己 clamp 修掉，见第 3 章 |
| **按 `structureSpawnWeight` 调不出密度** | 改成 10、100 都没变化 | 自定义坐标通道不参加 HBM 的槽位抽签，密度只看 `structureGridChunks`（N² 区块一处） |
| **结构槽位被占** | 某个群系一直不出现 | 槽位先被别的结构抽走了，提高权重或换群系 |
| **多方块机器** | 贴回来 core 认不出、变砖 | 结构里只保留**已成形**的机器；导出前确认机器是完整的多方块（core + 全部 dummy 都在），不要有方块缺失 |
| **跨区块截断** | 大结构边缘缺一块 | HBM 按区块裁剪写入，属于设计行为；结构越大越容易看到接缝，尽量让建筑边角落在一个区块内 |
| **`wand_air` 铺到建筑外面** | 生成后建筑外侧莫名多出空气缺口（`wand_air` 导出后就是空气） | 选区只框腔内；`--info` 看空气条目数，超预期就是铺多了 |
| **结构里的箱子是空的** | 模板没了 | 随机化是拿 NBT 里的物品当模板的，导出时箱子必须是满的；`saveArea` 只重映射 `items`/`Items` 两个键，自定义容器用别的键名会漏 |
| **每个遗迹箱子内容一模一样** | `structureLootRandomize` 被关了 | 配置里把它改成 `true`（默认就是 true，只有手动关过才会这样） |
| **关掉「生成结构」后遗迹不出现** | 新世界完全不生成 | 遗迹走 HBM 的 `StructureConfig.enableStructures`（默认 `flag` = 跟随世界的「生成结构」开关）。创建世界时别关它，或把 HBM 配置里的 `5.00_enableStructures` 改成 `true` |

## 8. 验证清单

0. **导出后先体检**（在仓库根目录跑）：
   ```
   python tools/structure_air_tool.py <导出的.nbt> --info
   ```
   对着输出核对三件事：尺寸对不对、空气条目是不是只有室内那几百格、
   `带 TE` 的条目数是不是等于箱子+机器的数量（少一个就说明有容器没存进去）。
1. 启动后看日志：
   ```
   [MNGA-Structures] [structure] 结构工具方块 ID（创世神填充用，仅本次加载有效）: wand_air=1952 → 填内部空气用 `//replace air 1952`；wand_structure=1957 → 手放保存方块用 `//set 1957`
   [MNGA-Structures] [structure] 遗迹已注册: dim=-1, size=41x13x38, y=0~3, grid=11 区块（每 121 区块一处）
   ```
   （`size` 就是结构实际尺寸，可以拿它核对导出是否漏了边角。）
2. 找不到文件时会打 warn，检查路径拼写和文件名后缀（`getName()` 会砍掉最后 4 个字符，
   所以 ResourceLocation 的 path **必须带 `.nbt`**）。
3. 开新世界（下界），往外跑。间距由 `structureGridChunks` 决定：默认 11 →
   平均每 121 区块（约 193×193 格）一处，也就是**每个 11×11 区块的格子里必有一处**，
   只是落点是 hash 出来的，不会在格子的固定角落。想看快一点就临时把它改成 6。
   （下界只注册了这一个结构，所以不存在「被别的结构抽走」的问题。）
4. **别再靠飞着找**（121 区块 + 埋在实心地狱岩里，走 50 个区块没撞见是常态）。
   直接跑工具读存档：
   ```
   python tools/structure_find.py "<存档目录>"
   python tools/structure_find.py "<存档目录>" --predict 10      # 去没探索过的区块蹲点
   ```
   生成瞬间日志里也会有一行 `地心实验室已生成: 底座 y=…`，带平面范围和区块坐标。
4. 允许作弊时可以直接定位：
   - 打开 `ServerConfig.STRUCTURE_DEBUG`，`wand_air` 会变成可见的调试方块，一眼看出结构范围。
   - 或者用 `/setblock` 手动放 load 版方块，在指定坐标贴一份检查外观与箱子内容。
5. 检查箱子：内容应比导出时少几格、数量也更零散，而且物品是散落在格子里的（不是从 0 号格排起）；
   开两个遗迹对比，同一箱子里少掉的东西、剩余数量、所在格子都应该不同。
6. 检查机器：打开 GUI，槽位和罐里的液体是不是导出时的状态。
7. 检查劣化：同一个存档找两座实验室，强化萤石/混凝土砖的破损程度应该明显不一样，
   但结构骨架上不该出现「整片塌掉」——出现就是 `DECAY_TABLE` 的概率写太高了。

## 9. 换名字 / 加第二个结构

- 换结构文件：改 `AddonStructures.RUIN_NBT`；同时改 `SPAWN_NAME` / `PIECE_NAME`。
- 加第二个遗迹：复制一份 `register()` 里的注册块，换 `RUIN_NBT`、`SPAWN_NAME`、`PIECE_NAME`。
  **注册名必须全局唯一**——`NBTStructure.registerStructure` 和 `JigsawPiece` 都按名字查重，
  重名会直接抛 `IllegalStateException`。
- 多个结构可以共用同一个 `RuinStart`（战利品逻辑一样），也可以各自带不同的战利品表。
- 劣化规则是**全局**的：`DECAY_TABLE` 按方块类型判定，不区分结构。
  如果两个结构对同一种砖块要有不同的破损率，把 `applyDecay` 加一个结构名参数，
  按 `parent.name` 分支即可。
